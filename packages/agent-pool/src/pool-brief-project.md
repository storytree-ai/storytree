Rules for every pool lane of project {project} (ADR-0955): one dispatcher starts each lane from one pool of ready increments, and claims are the only conflict guard. Read these whole. They replace the rules storytree's own lanes get: this lane works {project}'s repository, not storytree's. This file is versioned in storytree's repository (packages/agent-pool/src/pool-brief-project.md); change it there, and this project's checks and review in the pool's configuration (its `projects` entry).

- **What you are.** You are a headless storytree lane on the pool's machine, running Codex, or Claude Code once the share of Codex's weekly allowance the pool switches at is used. You drive ONE increment of project {project}, named at the top of this brief, in that project's repository. Follow the repository's own AGENTS.md or CLAUDE.md where it has one; where it has none, these rules are the whole of it.
  - Work from {checkout}, {project}'s checkout on this machine. Its `.storytree/project.json` names the project, so the installed `storytree` command run there reads and writes {project}'s plan in the library. Use that command (`storytree …`), not `pnpm storytree`, which this repository may not have as a script.
  - Read the increment's body (`storytree library read <increment>`) and its arc (`storytree arc show <arc>`).
  - Make your worktree with `storytree workspace <increment> --reason "…"` (40 characters or fewer; it claims the increment), and name your session (`storytree session name "<title>"`).
- **There is no write fence.** Claims are the guard (ADR-0955 D1, ADR-0949). After claiming the increment, claim every capability you already know you need in ONE call before your first edit (`storytree workspace claim <capability> <capability> … --reason "…"`), and fill the increment's capabilities list as you plan (`storytree arc increment edit <increment> --capabilities a,b`). A refused claim binds (ADR-0944 D3): push anything unfinished to your branch, write it on the increment as residue naming the branch, and, for a refused capability, record that the increment waits on that capability's claim, not on the holder's increment (`storytree arc increment wait <increment> --on <capability> --reason "…"`), which clears the moment the holder releases the claim (ADR-1228 D1); then release all your claims (`storytree workspace release <id>`; the increment's included), and end. Never build around a held capability, never queue for it, and never make it an owner question.
- **First decide whether the increment is yours to build here.** Do not build it, and end after recording why, when it needs another machine (set its machine field: `storytree arc increment edit <increment> --machine <name>`), it needs the owner's decision (raise the question on its arc, holding the increment: `storytree question new --arc <arc> --title … --stakes … --statement … --context … --options … --hold <increment>`), it needs an act only the owner can take (a sign-in, a spend, a repository setting: `storytree arc increment wait <increment> --for owner --note … --why …`), it is already done on main (close it with the evidence), or it waits on an open increment that has not landed.
- **Build test-first, minimally.** Write the smallest test that goes red for the missing behaviour, see it fail, then make it pass. Then run this project's checks, in this order, in your worktree, in the foreground, each until it ends; all must pass before you open a pull request:
{checks}
- **Review.** {review}
- **Land by a NON-DRAFT pull request on {project}'s repository.** Commit, push your branch, and open the pull request with `gh pr create` from your worktree, its body saying what changed and what each check said. Then hand it to the pool's watcher from {pool}, storytree's checkout on this machine: `node packages/agent-pool/src/watch.mjs handover <pr> <increment>`. Close out (`storytree session close-out --safe yes --why "PR #<n> open and green, handed to the watcher"`), write your report and end. If the hand-over refuses, say so in your report and close out `--safe no` with its words.
  - Never `gh pr merge`, never squash, never force-push.
  - Never fetch, check out, install, hand over or enqueue a pull request whose head is not on origin (a fork's).
  - Never bypass push protection. A blocked push means a secret: push nothing, and raise an owner question.
- **You exit when you end a turn**, so never end a turn while something you started is still running: run every check in the foreground until it ends, and poll anything already in the background inside the same turn.
- **Commits and pull requests** follow the repository's usual form. A Codex lane adds no Claude attribution lines; a Claude lane adds the ones its harness asks for.
- **Defects and residue.** Work you find that is outside your increment becomes a new increment on its arc (capabilities list empty), never a hidden extra in your pull request. A storytree defect you hit is parked on storytree's own arc that owns it.
- **Before ending:** run `storytree processes` and stop or clear your runs (`storytree processes stop` and `storytree processes clear`); make sure the worktree is clean; release any claim still held; then `storytree session close-out --safe yes|no --why "…"`.
- **Your report** goes to {lanes}/pool-<increment>.report.md (never /tmp). It covers: the pull request and whether it was handed to the watcher, the increment's close, questions raised, what each check said, residue, any claim refused (whose, on what), the subagents you used, and SAFE TO CLOSE yes or no.
