# Developer-home Windows privacy (contract 2.8)

`src/connect/dev-home-windows.test.ts` exercises the production creation and removal functions with disposable synthetic sign-ins. The Windows CI runner runs four native tests: creation beneath default and deliberately permissive parents, then legacy-home repair and refresh hand-back with an unchanged or conflicting source. The fixture paths include spaces, Unicode and shell metacharacters; paths travel as JSON on stdin, never executable PowerShell text.

Before copying credentials, the developer root is created with a protected, owner-only DACL whose grant inherits to files and directories. On removal, the known legacy directories, marker and copied sign-in are repaired before marker migration or conflict handling. Hand-back protects only the existing source sign-in file before writing refreshed bytes. Unrelated source settings and parent ACLs retain their original descriptors and contents. Windows permission errors abort the operation; chmod is no fallback.

The native tests ask Windows Authz to evaluate the actual on-disk security descriptors for the owner and an arbitrary unrelated SID with Everyone, Authenticated Users and BUILTIN Users groups. They require owner read/write/DACL access and refuse those rights to the unrelated identity, inspecting the home before the first sign-in write and the source file before hand-back. An intentionally permissive control shows the unrelated SID can read a synthetic source file even after chmod 0600. Conflict tests preserve both sign-ins and verify the retained developer-home ACLs; retry then hands the refresh back normally.

The Authz helper follows the already-landed automatic-backup proof, scoped here to this story's behavior. [Microsoft's Authz documentation](https://learn.microsoft.com/en-us/windows/win32/api/authz/nf-authz-authzinitializecontextfromsid) permits an arbitrary SID with AUTHZ_SKIP_TOKEN_GROUPS and explicitly supplied group SIDs. Directory creation uses the Windows PowerShell .NET Framework [Directory.CreateDirectory security overload](https://learn.microsoft.com/en-us/dotnet/api/system.io.directory.createdirectory?view=netframework-4.8.1), so the root receives its DACL at creation.

This measures Windows ACL authorization for a synthetic principal. It does not log in a second account, test a native desktop or real credentials, simulate administrator/backup privileges, revoke already-open handles, or prove resistance to concurrent path replacement by an adversary controlling the parent. Those are separate claims. No account, machine policy or service is changed. The non-Windows run visibly skips the four native tests; it runs the two injected permission-refusal regressions and the existing POSIX, marker and conflict tests. The refusal tests were observed red before the correction: copying continued to the build and hand-back succeeded without an ACL operation.
