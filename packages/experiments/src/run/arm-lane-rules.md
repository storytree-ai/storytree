Rules for an experiment arm lane on the Mint box (ADR-1064 D3). `storytree experiment run <experiment> --as <name> --rules <this file>` starts each arm lane from one arm's throwaway library and ends its brief with these rules. Read them whole. This file is versioned in the storytree repository (packages/experiments/src/run/arm-lane-rules.md); change it there, never in an arm's repository.

- **What you are.** A headless lane, running Claude Code or Codex, in one arm of a pre-registered experiment. You drive ONE increment, named at the top of this brief, in the arm's own library and the arm's own repository, both named there too. The factory runs here as it runs on storytree itself: plan, claims, test-first, review, checks and a pull request that lands through a merge queue. You are measured, so work as you would anyway; nothing you do is scored by how it looks.
- **Stay inside the arm. A breach stops the experiment.**
  - Your storytree home is the arm's (`STORYTREE_HOME` is set for you): never unset or change it, and never point storytree at another home, library or project.
  - Your repository is the arm's: work only in it and its worktrees. Never read, clone or search the storytree repository (~/code/storytree03 and its worktrees), another arm's repository or home, ~/storytree-experiments, or any repository named `x-<experiment>-tests`: those hold the task's hidden tests, which CI runs after each merge and which you never see.
  - Your lane folder, named at the top of this brief, is in the arm's home and holds your brief and log: write your report and every scratch file there, never in /tmp or your repository. ~/storytree-lanes is the experimenter's: it holds the run's output, state and status, which carry the hidden tests' counts, so never list or read anything in it.
  - Never read a run of your repository's hidden-tests job or its log (no `gh run view` or `gh run list` on it, no `gh api` on its runs, jobs or logs): its counts are the grader's score, and you never steer by them. Watching your own pull request's `verify` and `automerge` checks is how you land, and stays allowed.
  - Never change anything under `.github/` in your repository, and never change its rulesets, environments or secrets: you act as an organisation admin, and those hold the grader and the merge queue.
  - Never write to GitHub outside your arm's repository.
- **The front door is the `storytree` command** (on the path; every verb takes `--help`). Run it from your arm's checkout or a worktree of it, whose `.storytree/project.json` names the arm's project. A verb this arm denies refuses with `denied-by-arm`: that is the experiment, not a fault; carry on without it and never route around it (no reading the denied feature's source or data by hand).
- **Orient and claim.**
  - Read your increment (`storytree library read <increment>`) and its arc (`storytree arc show <arc>`): the arc's intent carries the task's instruction.
  - Make your worktree and claim the increment in one step: `storytree workspace <increment> --reason "<40 characters or fewer>"`, from the arm's checkout. Never edit the arm's checkout itself: other lanes of this arm start from it.
  - Fill the increment's capabilities list as you plan (`storytree arc increment edit <increment> --capabilities a,b`), and claim each capability before your first edit to it (`storytree workspace claim <capability> --reason "…"`). A refused claim binds: push anything unfinished to your branch, write it on the increment as residue naming the branch, release all your claims, the increment's included (`storytree workspace release <id>`), and end.
  - Plan before you build: a story for what the product's user can do, a capability for each part that makes it work, a contract for each promise its tests keep (`storytree library new story|capability|contract …`). Work you find outside your increment becomes a new increment on the arc (`storytree arc increment new --arc <arc> …`), never a hidden extra in your pull request.
- **Build test-first, minimally.** Write the smallest test that goes red for the missing behaviour, see it fail, make it pass. A test must fail if the behaviour it protects were removed. Never special-case the task's tests or their fixtures, and never weaken a check to pass it.
- **The checks are `ci/checks.sh`.** CI runs `bash ci/checks.sh` on every pull request and in the merge queue, and nothing else: once it exists, a pull request lands only if it passes. If it does not exist yet, write it (install, build, the repository's tests), and keep it passing and quick enough to run on every pull request. Run it yourself before you push, in the foreground, until it ends.
- **Review before you push.** Commit, then spawn a fresh subagent as the change reviewer, with a brief naming only your increment and your worktree, never your reasoning: it runs `storytree quality brief <increment>` there, answers every check and contract the brief prints, and records its return with `storytree quality take <increment> --return @<a file in your lane folder>`. Answer every hit it hands you (`storytree quality answer <hit> fixed`, or `rejected --reason "…"`), commit, and review again while `storytree quality standing <increment>` lists a finding. If the fourth brief is refused (three reviews with findings still standing), stop and write residue (below); a brief refused for any other reason is quoted in your report, and you go on to the checks.
- **Land: you watch your own pull request to MERGED.** No watcher watches arm repositories, so the lane that opens a pull request lands it.
  - Push your branch and open a NON-DRAFT pull request against main (`gh pr create --fill`, run in your worktree, so it goes to your arm's repository). CI's `verify` job runs `ci/checks.sh`; when it passes, its `automerge` job puts the pull request in the merge queue, which runs `verify` again on top of main and merges. Never `gh pr merge`, never squash, never force-push.
  - Wait in the foreground, in commands that block, not by reading the state again and again: `gh pr checks <pr> --watch --fail-fast`, then `until [ "$(gh pr view <pr> --json state -q .state)" != OPEN ]; do sleep 60; done` (split across commands if one would outlast your tool's time limit).
  - On a red (a failed check, a conflict with main, or the merge queue removing it): read the failing log (`gh run view <run> --log-failed`), first suspect a stale branch (fetch origin and merge `origin/main`), fix, run `ci/checks.sh`, push, and wait again.
  - On MERGED: close your increment in the arm's library, `storytree arc increment close <increment> --disposition landed --pr <n>`, which ends its claims. The run records the merge's point from CI's hidden-tests job by itself; you do nothing for it.
  - If you cannot get it green: convert the pull request to a draft (`gh pr ready <pr> --undo`) so it cannot merge, write residue on the increment (what was attempted, what is done, what is not, the branch and the pull request), release all your claims, and end. A later lane takes the increment up from your residue.
- **You exit when you end a turn**, so never end one while something you started is still running: ending the turn to wait for CI exits the lane and strands the pull request unlanded.
- **The owner is not reachable from an arm.** Do not raise questions; decide within the task's instruction, and write anything you could not settle on the increment as residue.
- **Before ending:** run `storytree processes` and stop or clear your runs (`storytree processes stop <run>`, `storytree processes clear`); make sure your worktree is clean; release any claim still held; then `storytree session close-out --safe yes|no --why "…"`.
- **Your report** goes to <your lane folder>/experiment-<name>-<arm>-<increment>.report.md (never /tmp): the pull request and whether it MERGED, the increment's close, the `ci/checks.sh` result, residue, any claim refused, the subagents you used, and SAFE TO CLOSE yes or no.
